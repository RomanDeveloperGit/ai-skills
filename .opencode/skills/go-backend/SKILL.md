# Go Backend

Практический набор правил для production Go-сервисов: HTTP/REST, фоновые воркеры и consumer'ы. Это не шаблон и не привязка к конкретному стеку: сначала конвенции проекта, затем ориентиры ниже. Для CLI, библиотек и скриптов бери только релевантные разделы. Выбирай минимально достаточные инструменты, а не модный набор. Если не можешь назвать таймаут, лимит, поведение при ошибке и способ закрытия ресурса — решение не готово.

## 1. Базовые принципы

- Любой внешний вызов принимает `context.Context`, имеет deadline и определённое поведение при отмене.
- У каждого ресурса есть владелец и способ закрытия. Открыл — зарегистрируй в lifecycle-менеджере или закрой в `defer`.
- Конфиг парсится и валидируется один раз до создания ресурсов. Лучше не запуститься, чем работать с половиной конфига.
- Ошибка логируется один раз — на границе, где принято решение о статусе ответа.
- Секреты, токены, cookies и PII не попадают в логи, ответы и метрики.
- Зависимости собираются явно в composition root; никаких глобальных singleton, `init()` с I/O и скрытых side effect.
- Слои и интерфейсы вводи по факту роста, а не заранее. Сначала простой срез, потом абстракция.
- Не добавляй зависимость, фреймворк или инфраструктуру, пока stdlib или уже принятый стек решают задачу.
- В существующем проекте сохраняй структуру, стиль и принятые библиотеки; меняй только то, что нужно задаче.
- Production-дефолт: явные таймауты, лимиты, retry с backoff, структурные логи, метрики и корректный shutdown.
- Любое изменение API, формата события или кода ошибки оценивай с точки зрения обратной совместимости.

## 2. Границы и структура

Ориентир для нового сервиса — слоистый монолит:

```text
cmd/<service>/main.go
internal/config
internal/model
internal/apperror
internal/transport/httpapi
internal/service
internal/repository
internal/infra/{db,broker,cache}
internal/platform/{logger,lifecycle,observability}
migrations/
scripts/
.env.example
```

- `transport` — DTO, валидация, HTTP-статусы, аутентификация на входе. Никакого SQL, бизнес-правил и публикации событий.
- `service` — сценарии и транзакционные границы. Не знает HTTP и не импортирует транспорт.
- `repository` — доступ к данным, маппинг ошибок драйвера, транзакции. Не содержит бизнес-правил.
- `model` — сущности и инварианты; без транспорта, БД и инфраструктуры.
- `apperror` — стабильные коды и безопасные сообщения; без HTTP-статусов и драйверов.
- `infra` — адаптеры внешних систем; `platform` — сквозные технические вещи. Ни те, ни другие не знают бизнес-сценариев.
- Зависимости направлены внутрь: transport → service → repository; model не зависит от остальных слоёв.
- Интерфейсы объявляй у потребителя, маленькими. Конструкторы возвращают конкретный тип.
- DTO отделяй от модели. Не отдавай наружу структуру БД «как есть».
- Пока сервис небольшой, держи плоские пакеты слоёв. При росте дели внутри слоя по фичам.
- Новый endpoint: DTO → handler → метод service → метод repository → миграция при необходимости → route → тесты.
- Не вводи DDD/CQRS/hexagonal и DI-фреймворк, пока проект не требует. Слоистый монолит — дефолт.
- Не делай generic repository и «базовые сервисы»: они скрывают доменные операции и мешают тестировать контракт.
- Циклические импорты запрещены; модель не должна знать о транспорте и БД.

## 3. Конфигурация

- Один типизированный конфиг; парсинг и валидация один раз в composition root, до создания пулов и клиентов.
- Ошибка конфига — fail fast с non-zero exit code. Паника допустима только если проект уже использует такой стиль.
- Все обязательные поля проверяй явно: required/notEmpty, enum, URL, порты, длительности, cross-field ограничения.
- Время — `time.Duration`, не «голые» числа. Денежные значения — не `float`.
- Env читает только конфиг. В handler, service и repository передавай типизированный конфиг или его часть; никаких `os.Getenv` по коду.
- Имена стабильные и сгруппированные: `HTTP_*`, `POSTGRES_*`, `KAFKA_*`, `RABBIT_*`, `SERVICE_*`, `SHUTDOWN_*`, `LOG_*`.
- `APP_ENV` — обычное строковое поле, если оно нужно. Не заводи отдельный тип `Env`, не делай по нему `switch` в логгере и не меняй формат логов от среды.
- Уровень логов — отдельный `LOG_LEVEL` с валидацией. Не выводи его из `APP_ENV`.
- Поведение задавай явными настройками (`LOG_LEVEL`, `HTTP_*`, `FEATURE_*`), а не неявными различиями между средами.
- Секреты — только через env или secret manager. Не логируй конфиг целиком и не коммить `.env`.
- Опциональные интеграции имеют явный `*_ENABLED`: если включены — валидируй параметры; если выключены — не создавай клиента и не требуй креды.
- В prod не полагайся на дефолты пула, таймаутов и shutdown: они должны быть заданы явно.
- `.env.example` дублирует каждую переменную с комментарием и безопасным примером; списки в нём и в локальном конфиге запуска не расходятся.

```dotenv
APP_ENV=local
SERVICE_NAME=orders-api
SERVICE_VERSION=0.1.0
LOG_LEVEL=debug

HTTP_ADDR=:8080
HTTP_READ_HEADER_TIMEOUT=5s
HTTP_READ_TIMEOUT=10s
HTTP_WRITE_TIMEOUT=15s
HTTP_IDLE_TIMEOUT=60s

POSTGRES_DSN=postgres://user:password@localhost:5432/app?sslmode=disable
POSTGRES_MAX_CONNS=20
POSTGRES_MIN_CONNS=2
POSTGRES_QUERY_TIMEOUT=3s

SHUTDOWN_TOTAL=40s
SHUTDOWN_HTTP=25s
SHUTDOWN_POSTGRES=5s
SHUTDOWN_KAFKA=10s
```

## 4. Логирование

- Используй `log/slog` с JSON-handler во всех средах: local, test, staging, prod. Никаких text/color/custom handler, переключаемых по env.
- `APP_ENV` может быть полем лога, но не переключателем handler'а и уровня. Уровень — только `LOG_LEVEL` из конфига.
- Локально JSON читай внешним просмотрщиком логов; красивый вывод — задача инструмента, а не production-кода.
- База лога: `service`, `version`, при необходимости `env`. Source добавляй осознанно: полезен для диагностики, но даёт накладные расходы.
- Логгер создаётся один раз в composition root и передаётся явно. Глобальный logger — только для библиотек, которым он действительно нужен.
- До загрузки конфига поставь bootstrap JSON logger, иначе ошибка конфига уйдёт в стандартный text-логгер. После загрузки замени его настроенным.
- В контекстные логи добавляй `request_id`, `trace_id`, при наличии — `user_id`/`tenant_id`. Ключи контекста делай неэкспортируемыми типами.
- Access log: method, шаблон route без ID, status, duration, request_id, размер ответа. Тело, query, cookies и заголовки по умолчанию не логируй.
- Логируй ошибку один раз — на границе. 4xx — `info`/`debug` без stack, 5xx — `error` с cause. Не дублируй один `err` в repository, service и transport.
- Оборачивай ошибки через `%w`; в лог передавай саму ошибку, а не только её текст.
- Panic recovery логирует stack и возвращает 500. Panic не используется для бизнес-ошибок.
- Не логируй пароли, токены, `Authorization`, cookies, платёжные данные, email/телефон и другие PII. Редактируй чувствительные поля до записи.
- Не используй `fmt.Print*` и `log.Printf` для прикладного логирования.
- При высоком QPS можно сэмплировать access-логи, но 5xx не сэмплируй.

## 5. HTTP и REST

- Router и HTTP-фреймворк выбирай по проекту. Правила ниже не зависят от конкретной библиотеки. Не включай debug-режим фреймворка в prod.
- Группируй роуты под `/api/v1`; версию меняй только при breaking change. Ресурсы — существительные во множественном числе.
- Handler: bind → validate → service → response. Никакой бизнес-логики, SQL и публикации событий.
- DTO отделяй от модели. Явные JSON-теги; не отдавай наружу структуру БД «как есть».
- Валидация на границе: собирай все ошибки полей сразу, а не первую. Лимит тела — явный (`http.MaxBytesReader` или настройка фреймворка).
- Проверяй `Content-Type` для body-запросов; для JSON можно отклонять неизвестные поля, если это не ломает клиентов.
- Порядок middleware: recovery → request_id → access log → body limit → authn → rate limit → handler. Контекст и request_id должны быть доступны ниже.
- Таймауты задавай на `http.Server`: `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout`, `MaxHeaderBytes`. `http.TimeoutHandler` не заменяет отмену контекста и таймауты зависимостей.
- Бери `c.Request.Context()` / `r.Context()`. Не создавай фоновые горутины с request context без явного detached-контекста и собственного таймаута.
- Статусы: 200/201/204 — успех; 400 — кривой запрос; 401/403 — доступ; 404 — нет ресурса; 409 — конфликт; 422 — семантическая валидация; 429 — лимит; 500 — неизвестная ошибка; 502/503/504 — проблемы зависимости. Не возвращай 200 с ошибкой.
- 202 — только если работа реально асинхронная. 204 — без тела.
- Пагинация: `limit` по умолчанию 20, максимум 100; для больших выборок — cursor, а не глубокий offset. Порядок сортировки стабильный.
- Request ID: принимай входящий `X-Request-ID` только после проверки формата, иначе генерируй UUID; возвращай в ответе и клади в контекст. Trace ID проверяй так же.
- Аутентификация — в middleware, авторизация по ресурсу — в service. Handler не парсит токены и не проверяет ownership.
- Для POST с побочными эффектами поддерживай idempotency key, если клиент может повторить запрос.
- Ответ с ошибкой собирай в одном helper'е; какие app errors раскрывать — решает операция. Не отдавай сырой `err.Error()` клиенту.
- Health: liveness не зависит от БД и брокеров; readiness проверяет только критические зависимости с коротким таймаутом. Не смешивай их.
- CORS, secure headers, TLS termination и rate limit обычно живут на прокси/ingress; в приложении оставляй только необходимое.
- Не используй `time.Sleep` для «подождать, пока сервер стартует». Создавай listener синхронно или жди readiness; ошибка bind должна ронять сервис.

## 6. Ошибки и контракт API

Разделяй три слоя:

1. HTTP status — транспортная семантика.
2. `error.code` — стабильная бизнес-причина, по которой ветвится клиент.
3. `message` и `details` — безопасное объяснение и структурированные детали.

```json
{
  "error": {
    "code": "ERR_ORDER_NOT_FOUND",
    "message": "order not found",
    "details": [
      { "field": "items[0].quantity", "code": "ERR_FIELD_MIN", "message": "must be at least 1" }
    ]
  },
  "request_id": "0192f3c4-..."
}
```

- `error.code` — `ERR_<DOMAIN>_<REASON>`, `SCREAMING_SNAKE_CASE`. Клиент ветвится по `code`, а не парсит `message`. Не меняй и не удаляй код без версии API.
- `message` — короткий безопасный fallback. SQL, stack, имена таблиц и внутренние детали в него не попадают.
- `details` — опционально; для валидации — все поля сразу.
- Если в проекте уже есть envelope ошибок, сохрани его. Инварианты выше важнее формы.
- `request_id` — для логов и поддержки, не заменяет код.
- Прикладные ошибки отделяй от транспорта: они описывают бизнес-причину и не содержат HTTP-статуса. Статус выбирает транспорт на уровне конкретной операции.
- Прикладная ошибка должна сохранять идентичность при оборачивании. Сравнивай через `errors.Is/As`, никогда по строке.
- Детали валидации — отдельный тип с полями `field`, `code`, `message`; `field` — JSON-имя, не имя Go-поля. Не вставляй в сообщение значения, которые могут содержать PII.
- Repository переводит известные ошибки драйвера в прикладные: no rows → not found, unique violation → conflict, FK violation → conflict/invalid reference. Контекстные ошибки пропускай наверх.
- Неизвестную ошибку оборачивай с контекстом операции и отдавай наверх. Не склеивай техническую и прикладную ошибку в одну ради лога: это размывает тип и делает сообщение нечитаемым.
- HTTP-маппинг — на уровне операции, а не один на весь transport. Один и тот же app error в разных методах может давать разные статусы или 500, если не входит в контракт метода.
- Неизвестная ошибка → 500 `ERR_INTERNAL` с `internal server error`. Не маскируй её под 400 «на всякий случай».
- 4xx — `info`/`debug` без stack; 5xx — `error` с cause. Не логируй одну ошибку на каждом слое.
- `context.Canceled` — клиент ушёл: ответ не пиши и не шуми error-логом. `context.DeadlineExceeded` — 504 `ERR_TIMEOUT` или 503; выбери одно и придерживайся.
- Panic не используй для бизнес-ошибок. Recovery middleware логирует stack и возвращает 500, если ответ ещё не начат.
- Для ownership-проверок часто безопаснее 404, чем 403: не раскрывай существование чужого ресурса. Реши на уровне продукта и придерживайся.
- Не возвращай клиенту `sql: no rows`, имя таблицы, stack или внутренний код драйвера.

## 7. Данные и транзакции

- Для нового сервиса предпочтителен современный пул с явной настройкой; если проект уже на другом драйвере или пуле, не мигрируй ради моды.
- Один пул на процесс; проверяй соединение с таймаутом на старте и закрывай через lifecycle-менеджер.
- Настраивай пул из env: максимум/минимум соединений, время жизни, idle timeout, health check. Учитывай лимит БД и число реплик сервиса.
- На каждый запрос — контекст с таймаутом; не полагайся только на серверный таймаут. Транзакции держи короткими.
- SQL — только в repository. Явные колонки и явный маппинг результата; `SELECT *` в production-коде не используй.
- Параметризуй запросы; не склеивай SQL из пользовательских строк.
- Транзакция: начать → `defer Rollback` → работа → `Commit`; ошибку commit проверяй отдельно. Если commit вернул ошибку, результат неизвестен: не retry'и слепо, если операция не идемпотентна.
- Внешние вызовы внутри транзакции запрещены. Для событий используй outbox или другой явный механизм согласованности.
- Маппинг: no rows → not found; unique violation → conflict; FK violation → conflict/invalid reference; serialization/deadlock → bounded retry с backoff. Остальное оборачивай и отдавай наверх.
- Миграции — отдельная директория и принятый в проекте инструмент. Одна миграция — одно логическое изменение; обязательны up и down.
- Приложение не запускает миграции в prod автоматически. Это отдельный job/CI-шаг с блокировкой от параллельного запуска.
- Breaking changes — expand/contract: сначала добавь новое, задеплой, потом удали старое. Большие индексы создавай без блокировки таблицы.
- Backfill — батчами с throttling, отдельным job, а не одним `UPDATE` на миллионы строк. Перед destructive-миграцией — backup и rollback-план.
- Деньги — `numeric`, время — `timestamptz` в UTC, идентификаторы — `uuid`/`bigint`. JSONB — только для действительно гибких данных.
- Индексы — под реальные запросы. Slow query проверяй планом выполнения, N+1 не оставляй.
- Для больших списков — cursor-пагинация и стабильный `ORDER BY`.

### Кэш

- Кэш — оптимизация, а не источник истины. Если кэш недоступен, чтение должно по возможности деградировать до БД, а не падать.
- Используй cache-aside: читать из кэша → при промахе читать БД → заполнить кэш с TTL. Инвалидируй после успешной записи.
- Не кэшируй ошибки и `nil` без явного negative-cache с коротким TTL.
- Продумай stampede: дедупликация запросов, лок или jitter TTL для горячих ключей.
- Ключи версионируй, если меняется формат значения.

## 8. Асинхронная работа

- Выбирай брокер по семантике: event log и порядок по ключу — один класс систем; task queue, routing и delayed retry — другой. Не смешивай подходы без причины.
- Публикуй события после commit в БД через outbox. Прямая двойная запись допустима только как осознанный временный компромисс с reconciliation.
- Один producer/connection на процесс; закрывай через lifecycle-менеджер. Async producer обязан читать error channel и иметь метрику ошибок.
- Ключ сообщения — ID агрегата, чтобы сохранить порядок по нему. Без ключа порядок не гарантирован.
- Конверт события: `event_id`, `type`, `version`, `occurred_at`, `trace_id`, `payload`. Изменения — backward-compatible; consumer терпим к неизвестным полям.
- Consumer group: коммить offset/ack после успешной обработки; retry ограничен, затем DLQ. Не блокируй партицию навсегда.
- Consumer должен быть идемпотентным: at-least-once — норма, дубликаты возможны.
- Для poison message — bounded retry с backoff/jitter → DLQ. Не делай бесконечный requeue.
- Настраивай prefetch/concurrency под ёмкость зависимостей, а не «побольше».
- Shutdown consumer'а: перестать читать → дождаться in-flight → закоммитить offset/ack → закрыть group.
- Shutdown producer'а: flush → close, чтобы не потерять подтверждённые события.

## 9. Lifecycle и graceful shutdown

Не размазывай shutdown по `main` и инфраструктурным пакетам. Раздели две роли:

- **Actor** — долгоживущий компонент с операцией запуска, принимающей контекст: HTTP-сервер, consumer, воркер. По отмене контекста он перестаёт принимать работу, дренирует in-flight и сигнализирует, если остановка была аварийной.
- **Closer** — ресурс с операцией закрытия, принимающей контекст: пул БД, producer, кэш, файлы. Closers регистрируются в менеджере в порядке создания и закрываются в обратном порядке.

Менеджер lifecycle — это небольшой локальный слой, а не фреймворк:

- Closer регистрируется с именем и таймаутом на этапе сборки; закрытие идемпотентно.
- Каждый closer получает свой таймаут; общий бюджет ограничивает всю процедуру.
- Closers закрываются последовательно LIFO: зависимые ресурсы раньше базовых.
- Ошибки всех closers агрегируются в одну; одна ошибка не мешает закрыть остальные.
- Контракт closer'а — уважать контекст. Стороннее закрытие без контекста оборачивай адаптером; если оно зависло, таймаут не сможет его прервать — это допустимо только на финальном shutdown.

Порядок запуска и остановки:

- Старт: конфиг → логгер → инфраструктура → transport. Ошибка на любом шаге — закрыть уже созданные ресурсы и выйти non-zero.
- Запускай actors через группу с общим контекстом: фатальная ошибка отменяет остальных, ожидание дожидается остановки.
- После отмены сигнального контекста сразу отмени подписку на сигналы, чтобы второй сигнал завершил процесс немедленно.
- Штатная остановка: HTTP/consumer'ы (дренаж) → producers (flush/close) → БД/кэш → файлы/логи.
- Не закрывай БД раньше HTTP/consumer'ов: in-flight запросы получат ошибки.
- Общий бюджет shutdown должен быть меньше grace period платформы с запасом на drain трафика.
- Передача слушающего сокета нужна только там, где нет оркестратора и дренажа через балансировщик.
- `os.Exit` — только в `main`; не из горутин. Graceful exit — код 0, ошибка старта/остановки — non-zero.
- Liveness не зависит от БД и брокеров; readiness проверяет только критические зависимости.
- Дренаж сервера не ждёт hijacked-соединения (WebSocket, кастомный SSE); их нужно отслеживать отдельно.
- Для shutdown используй `context.Background()`, а не отменённый request context.
- Актор не должен молча возвращать `nil`, если сервис должен продолжать работать. Неожиданная остановка — ошибка.
- Не используй `time.Sleep` для синхронизации старта. Создавай listener синхронно или жди readiness.
- Готовый lifecycle-механизм допустим, если он уже принят в проекте. Не тащи фреймворк только ради shutdown.

## 10. Надёжность и безопасность

- Аутентификация — на входе, авторизация — в service, по ресурсу и действию. Не полагайся на то, что UI скрывает кнопку.
- Валидируй все входные данные на границе; ограничивай тело, размеры файлов, глубину JSON, количество элементов в batch.
- Rate limit — на дорогие и чувствительные операции; возвращай 429 с `Retry-After`.
- Секреты — только из env/secret manager; не логируй и не отдавай в ответах. Ограничивай права и ротируй.
- TLS обычно терминируется на ingress/прокси; внутри периметра всё равно проверяй, какие данные передаются.
- Не собирай SQL/HTML/URL из пользовательских строк без экранирования. Для исходящих URL проверяй SSRF-риски.
- Retry — только для идемпотентных операций или с idempotency key; ограниченный, с backoff и jitter. Не retry'и 4xx, validation и business errors.
- Circuit breaker/bulkhead — только под наблюдаемую проблему; сначала таймауты, лимиты пула и backpressure.
- Деградируй осознанно: кэш или второстепенный сервис может быть недоступен, но основной сценарий должен работать, если это допустимо бизнесом.
- Не делай бесконечные очереди в памяти; используй bounded channels и метрику переполнения.
- Идемпотентность POST с побочными эффектами — через idempotency key или естественный уникальный ключ.
- Для каждого внешнего вызова определи: timeout, retry, лимит, поведение при отмене и что видит пользователь при отказе.

## 11. Observability

- Логи — JSON, коррелированные `request_id`/`trace_id`; без секретов и PII.
- Метрики: HTTP RED (rate, errors, duration), пул БД, consumer lag, ошибки publish/consume, retry, DLQ, длительность shutdown.
- Бизнес-метрики — по ключевым сценариям, без кардинальности на пользователях.
- Трейсинг — если он уже принят в проекте; иначе не тащи отдельную систему. Пробрасывай стандартный контекст трассировки и не подменяй его самодельным ID.
- Health: liveness не зависит от внешних систем; readiness проверяет критические зависимости с коротким таймаутом. Не делай readiness тяжёлым.
- Debug-эндпоинты — только на внутреннем порту или за аутентификацией.
- Алерты — по симптомам (SLO, error rate, latency, saturation, lag), а не по каждому логу ошибки.
- Не логируй по одному запросу несколько раз; access log и error log должны дополнять, а не дублировать друг друга.

## 12. Тесты, tooling и CI

- Unit-тесты — table-driven; handler — через тестовый HTTP-сервер; маппинг ошибок — отдельной таблицей по операциям.
- Repository и миграции проверяй на реальной БД в изолированном окружении, драйвер не мокай.
- Брокеры в unit-тестах — через интерфейс и fake; интеграционные тесты — опционально, с тегом.
- Тестируй поведение и контракт, а не приватную реализацию. Проверяй 400/401/403/404/409/422/429/500, отмену контекста и таймауты.
- `go test -race ./...`; без `time.Sleep` для синхронизации, только polling с контекстом.
- Graceful shutdown проверяй тестом: медленный in-flight запрос + сигнал; запрос должен завершиться, ресурсы закрыться, второй сигнал — убить процесс.
- Миграции проверяй на чистой БД: up → down → up; down должен реально откатывать.
- Нагрузочные тесты — для критичных endpoint'ов и consumer'ов; смотри p95/p99, ошибки, насыщение пула и lag.
- Единая точка входа для команд: форматирование, lint, тесты, интеграционные тесты, запуск, сборка, миграции. Версии инструментов фиксируй.
- CI: `go vet`, `go test -race ./...`, lint, build, проверка миграций, сканер уязвимостей. Кэшируй модули и инструменты.
- `.env.example` и локальный конфиг запуска держи синхронно; в example — комментарии и безопасные значения, без реальных секретов.
- Новая зависимость обоснована, зафиксирована и не дублирует уже принятую.

## 13. Как действовать агенту

1. Сначала изучи проект: `go.mod`, структуру, конфиг, логгер, обработку ошибок, слой данных, тесты, деплой. Не навязывай свой стек.
2. Уточни контракт задачи: входы/выходы, ошибки, таймауты, лимиты, изменения схемы, обратную совместимость.
3. Найди существующий паттерн и переиспользуй его. Новый слой или абстракцию добавляй только при реальной необходимости.
4. Делай минимальный вертикальный срез: DTO → handler → service → repository → миграция → тесты.
5. Явно определи поведение при отказах: что ретраить, что логировать, что видит клиент, что происходит при shutdown.
6. Закрой ресурсы и зарегистрируй их в lifecycle-менеджере; не оставляй горутины и фоновые задачи без отмены.
7. Добавь наблюдаемость: лог на границе, метрики ключевого сценария, health/readiness при необходимости.
8. Прогони format, lint, `go test -race ./...`, build. Для изменения схемы проверь up/down и план отката.
9. В отчёте укажи, что изменено, какие риски, что не проверено и какие решения требуют подтверждения.

## 14. Чеклист перед PR/релизом

- [ ] У нового endpoint есть DTO, валидация, service, repository и тесты.
- [ ] Все внешние вызовы принимают context и имеют таймаут.
- [ ] Ошибки замаплены на уровне операции; сырые внутренности не уходят клиенту.
- [ ] 4xx не логируются как error, 5xx логируются с cause и `request_id`.
- [ ] SQL использует индексы; миграция имеет рабочие up/down; транзакции короткие.
- [ ] Retry ограничен; DLQ/outbox/idempotency продуманы.
- [ ] Новый ресурс закрывается через lifecycle-менеджер; второй сигнал по-прежнему убивает процесс.
- [ ] Бюджет shutdown укладывается в grace period платформы с запасом на drain.
- [ ] Переменные добавлены в `.env.example` и локальный конфиг запуска; секретов в репозитории нет.
- [ ] Логи JSON, структурные, без секретов и PII; `request_id`/`trace_id` передаются дальше.
- [ ] `go test -race ./...`, `go vet`, lint и format проходят.
- [ ] Новая зависимость обоснована и зафиксирована.
- [ ] Breaking change API/кода ошибки версионирован и задокументирован.
- [ ] Health/readiness и ключевые метрики не забыты.
