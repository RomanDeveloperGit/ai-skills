# Frontend Pages-First

Строй FSD от страницы: страница — единица декомпозиции, нижние слои — результат реального переиспользования.

## 1. Ядро

- Начинай любую задачу с вопроса: «На какой странице и в каком сценарии это используется?».
- Держи код там, где он используется. Один потребитель — код внутри страницы.
- Считай потребителем другой слайс: другую страницу, фичу, сущность или виджет. Два компонента на одной странице — не два потребителя.
- Извлекай в нижний слой только после появления второго реального потребителя.
- Не создавай `entities`, `features`, `widgets` и пустой `shared/ui` «на будущее».
- Не дроби нижний слой на микрослайсы. Один слайс — один домен, действие или самостоятельный блок.
- Если сомневаешься между страницей и нижним слоем, оставляй на странице. Извлечь позже дешевле, чем распутывать преждевременную абстракцию.
- Дублирование двух похожих, но разных сценариев допустимо. Обобщай только при совпадающем контракте.

## 2. Выбор места

Применяй алгоритм по порядку:

1. Это bootstrap или инфраструктура приложения: роутер, провайдеры, env, HTTP-клиент, авторизация, глобальные стили? → `app` или `shared`.
2. Это используется только одной страницей? → `pages/<page>/`.
3. Это доменные данные, состояние или API, нужные двум и более страницам? → `entities/<domain>/`.
4. Это пользовательское действие с UI, нужное двум и более страницам? → `features/<action>/`.
5. Это самостоятельный составной UI-блок, нужный двум и более страницам? → `widgets/<block>/`.
6. Это примитив или утилита без домена, нужные двум и более местам? → `shared/`.
7. Ничего не подошло → вернись на страницу и не извлекай.

Уточнения:

- Инфраструктура — то, без чего приложение не работает. Одноразовый `Button` или `format-date` не инфраструктура: жди второго потребителя.
- Код, нужный двум блокам одной страницы, остаётся локальным для страницы.
- Если двум страницам нужен только одинаковый запрос, выноси API и модель домена в `entities`, а UI оставляй на страницах.
- Если двум страницам нужен только одинаковый визуальный блок без своего домена, выноси его в `widgets` или `shared/ui` по смыслу.
- Не создавай сущность только потому, что у неё есть тип или endpoint. Сущность оправдана общим состоянием, API или каноническим отображением.

## 3. Структура

### 3.1. Обязательные слои

По умолчанию держи только три слоя:

- `app` — инициализация, провайдеры, роутер, error boundary, глобальные стили, env.
- `pages` — route-level экраны и их сценарии.
- `shared` — инфраструктура и примитивы без знания о домене.

`entities`, `features`, `widgets` добавляй только при реальном переиспользовании. Пустые папки не создавай.

### 3.2. Плоская страница

Начинай страницу с плоских файлов:

```text
pages/orders/
  index.ts        # публичный API страницы
  ui.tsx          # корневой компонент
  model.ts        # бизнес-модель страницы
  api.ts          # запросы только этой страницы
  lib.ts          # чистые функции только этой страницы
  config.ts       # константы страницы
  types.ts        # типы страницы
```

Правила:

- Создавай файл только при необходимости. Не оставляй пустые `api.ts`, `lib.ts`, `types.ts`.
- `index.ts` — единственный public API страницы.
- `ui.tsx` — корень, а не набор несвязанных компонентов.
- `model.ts` — бизнес-модель страницы.
- `api.ts` — только запросы страницы. Если запрос нужен другой странице, переноси его в `entities`.
- `lib.ts` — чистые функции без React, Effector и HTTP.
- `types.ts` — типы страницы.

### 3.3. Выросшая страница

Разворачивай файлы в папки, когда появляется 3+ самостоятельных блока или файл становится трудно навигировать:

```text
pages/orders/
  index.ts
  ui/
    Page.tsx
    Filters.tsx
    OrderCard.tsx
    order-list/
      ui.tsx        # корень блока OrderList
      Empty.tsx
      Error.tsx
  model/
    orders.ts      # бизнес-модель
  api/
    requests.ts
  lib/
    format.ts
```

Правила:

- Держи `ui/`, `model/`, `api/`, `lib/` плоскими: максимум один уровень внутри.
- Группируй по смыслу или визуальным блокам, а не по типам файлов.
- Не создавай папку ради одного файла.
- Не создавай `index.ts` во внутренних папках: только на границе слайса.
- Не используй `components/`, `hooks/`, `utils/`, `helpers/` внутри страницы: файл уже называет роль.
- Имя папки называет домен или блок, имя файла — роль. Не повторяй контекст: `ui/order-list/ui.tsx`, а не `ui/order-list/OrderList.tsx`.
- Называй файлы `model` по бизнес-контексту: `orders.ts`, `checkout.ts`, `conversation.ts`; не `store.ts`, `effects.ts`.
- Не дроби `model` на `store.ts`, `effects.ts` или отдельные папки под них без необходимости. Начинай с одного файла по бизнес-контексту; разделяй, когда файл разросся или части модели действительно независимы.

### 3.4. Анатомия страницы

| Файл/папка | Ответственность |
|---|---|
| `index.ts` | Публичный API: компонент и только то, что нужно снаружи |
| `ui.tsx` / `ui/Page.tsx` | Layout, композиция блоков, состояния загрузки, пустоты и ошибки |
| `ui/<block>/` | Самостоятельный визуальный блок страницы |
| `model.ts` / `model/` | Бизнес-состояние, события, эффекты, селекторы, инициализация и очистка |
| `api.ts` / `api/` | Запросы, специфичные для страницы |
| `lib.ts` / `lib/` | Чистые функции страницы |
| `config.ts` | Константы, лимиты, тексты, ключи |

Страница:

- знает про route params и свой жизненный цикл;
- компонует блоки и может быть содержательной;
- не импортирует другую страницу;
- имеет явные состояния: загрузка, пустота, ошибка, готовность.

### 3.5. Опциональные слои

| Слой | Когда создавать | Что хранит | Может импортировать |
|---|---|---|---|
| `widgets` | Блок нужен 2+ страницам | Самостоятельный составной UI и его модель | `features`, `entities`, `shared` |
| `features` | Действие с UI нужно 2+ страницам | Пользовательское действие, форма, диалог, его модель | `entities`, `shared` |
| `entities` | Домен нужен 2+ страницам или фичам | Модель, состояние, API, селекторы, канонический UI | `shared` |

Правила:

- `entities`: UI клади только при каноническом отображении, одинаковом в нескольких местах (`UserAvatar`, `OrderStatusBadge`). Остальной UI остаётся на страницах.
- `features`: не знай о layout страницы. Контекст передавай через props или события.
- `widgets`: это не «большой компонент», а блок с собственным смыслом и жизненным циклом.
- Не создавай виджет, если блок используется на одной странице: держи его в `pages/<page>/ui`.

### 3.6. app и shared

`app`:

- `app/router` — конфигурация React Router, guards, layout, error boundary.
- `app/providers` — провайдеры темы, ошибок, уведомлений.
- `app/styles` — reset, токены тёмной темы, глобальные стили.
- `app/env` — запуск валидации env через Zod при старте.

`shared`:

- `shared/api` — настроенный Ky-клиент, нормализация ошибок, auth header.
- `shared/ui` — собственные примитивы и дизайн-система без домена, используемые 2+ местами.
- `shared/lib` — чистые утилиты без домена.
- `shared/config` — общие константы, runtime-конфиг и Zod-схема env.
- `shared/router` — только общие контракты маршрутов, если путь нужен 2+ местам.

Запрещено:

- импортировать домен в `shared`;
- создавать `shared/components`, `shared/hooks`, `shared/utils` как свалку;
- подключать UI-библиотеку: компоненты пиши с нуля;
- хранить в `shared` страничные сценарии;
- создавать `processes`, `modules`, `services`, `store`, `types` на верхнем уровне.

Направление импортов:

```text
app → pages → widgets → features → entities → shared
```

Импортируй только вниз. Не импортируй слайсы одного слоя друг в друга. Страница не импортирует страницу.

## 4. Именование

- Папки — `kebab-case`.
- Файлы компонентов — `PascalCase.tsx`; корневой файл слайса или блока — `ui.tsx`. Имя файла называет роль (`Page.tsx`, `Card.tsx`), имя экспорта может уточнять контекст (`OrdersPage`, `UserCard`).
- Хуки, утилиты, модели, API — `kebab-case.ts`.
- Компоненты — `PascalCase`; функции и переменные — `camelCase`; константы — `UPPER_SNAKE_CASE`; типы — `PascalCase`.
- Сторы — `$orders`; эффекты — `loadOrdersFx`; команды — `retryClicked`, `pageMounted`; факты — `ordersLoaded`.
- API-модули — `ordersApi`; схемы — `orderSchema`; типы — `Order`.
- Тесты — `<subject>.test.ts(x)` рядом с субъектом.

Не дублируй контекст:

```text
Плохо: pages/user/ui/UserCard/UserCard.tsx
Хорошо: pages/user/ui/Card.tsx        // экспорт UserCard
Плохо: pages/orders/ui/OrdersPage/OrdersPage.tsx
Хорошо: pages/orders/ui/Page.tsx      // экспорт OrdersPage
Плохо: pages/orders/model/store.ts
Хорошо: pages/orders/model/orders.ts
```

Не используй без квалификатора: `data`, `item`, `list`, `info`, `utils`, `helpers`, `common`, `manager`, `service`, `handler`. Исключение — короткая локальная переменная с очевидным контекстом.

## 5. Public API и импорты

- Один `index.ts` на слайс. Он определяет внешний контракт.
- Экспортируй только то, что реально используется снаружи. Внутренний файл или функция не попадают в `index.ts`.
- Запрещён `export *`. Только явные `export { ... }` и `export type { ... }`.
- Не экспортируй внутренние сторы, хелперы, API-функции и константы, если снаружи они не нужны.
- Не создавай barrel-файлы внутри слайса.
- Снаружи импортируй только через public API слайса. Внутри слайса — относительные пути.
- Запрещены глубокие импорты: `@/pages/orders/ui/Page`, `@/entities/order/model/history`.
- Используй один алиас `@/*` → `src/*`. Не создавай алиасы на каждый слой.
- Не допускай циклов. При цикле выноси общий контракт вниз, инвертируй зависимость через событие или объединяй слайсы. Не лечи цикл ленивым импортом.

Пример:

```ts
// pages/orders/index.ts
export { OrdersPage } from './ui/Page';
export type { OrdersPageProps } from './ui/Page';
```

```ts
// снаружи
import { OrdersPage } from '@/pages/orders';
```

```ts
// внутри страницы
import { OrderCard } from './OrderCard';
import { loadOrdersFx } from '../model/orders';
```

Не прячь регистрацию подписок в побочный импорт модуля. Вызывай инициализацию и очистку явно из page UI или route loader.

## 6. Состояние и Effector

### 6.1. Один владелец

| Состояние | Владелец |
|---|---|
| Текст в поле, открытая модалка, hover | Компонент, `useState` |
| Фильтры, пагинация, вкладка | URL или React state |
| Бизнес-данные страницы | `model` по контексту |
| Доменные данные, общие для страниц | Entity model |
| Сессия, тема, уведомления | `app` или `shared` |

Не копируй одни данные в два стора. Один источник правды, остальное — селекторы.

### 6.2. Асинхронное состояние

Используй discriminated union вместо набора флагов:

```ts
type AsyncState<T> =
  | { status: 'idle' }
  | { status: 'pending' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: AppError };
```

- `isEmpty` — это `status === 'success' && data.length === 0`, а не отдельный флаг.
- Не смешивай `isLoading`, `isError`, `isSuccess`, `isEmpty` в один набор.
- При повторной загрузке сохраняй предыдущие данные отдельно, если это нужно UX.
- Ошибка должна иметь действие восстановления: повторить, вернуться, изменить данные.

### 6.3. Поток данных

```text
UI event → page/feature event → effect → API → owner store → selector → UI
```

- Компонент не вызывает API напрямую.
- Компонент не оркестрирует несколько эффектов.
- Эффект делает side effect и возвращает типизированный результат.
- Стор обновляет только владелец.
- Производные значения считай селектором, а не храни отдельно.

Пример бизнес-модели страницы:

```ts
// pages/orders/model.ts
import { createEffect, createEvent, createStore, sample } from 'effector';

import { toAppError } from '@/shared/api';

import { ordersApi } from './api';
import type { AsyncState, Order } from './types';

export const pageMounted = createEvent();
export const retryClicked = createEvent();

export const loadOrdersFx = createEffect(async () => ordersApi.getOrders());

export const $orders = createStore<AsyncState<Order[]>>({ status: 'idle' })
  .on(loadOrdersFx, () => ({ status: 'pending' }))
  .on(loadOrdersFx.doneData, (_, data) => ({ status: 'success', data }))
  .on(loadOrdersFx.failData, (_, error) => ({
    status: 'error',
    error: toAppError(error),
  }));

sample({
  clock: [pageMounted, retryClicked],
  target: loadOrdersFx,
});
```

```tsx
// pages/orders/ui.tsx
const { state, retry } = useUnit({
  state: $orders,
  retry: retryClicked,
});
```

Правила Effector:

- Используй `useUnit` с объектом, а не длинные массивы.
- Для инициализации страницы вызывай `pageMounted` из route loader или `useEffect`; очищай подписки при unmount.
- Учитывай StrictMode: инициализация должна быть идемпотентной или отменяемой.
- `combine` — для производного состояния, `createApi` — для точечных обновлений.
- Не держи UI-логику в эффектах.
- Не используй `useEffect` для бизнес-логики, которую можно выразить через `sample`.
- Не заводи отдельные файлы под каждый стор и эффект; держи модель одним файлом, пока она остаётся связной.

### 6.4. Отмена и гонки

- Отменяй запрос при уходе со страницы, смене фильтра и повторном запросе.
- Передавай `AbortSignal` в Ky или храни `AbortController` рядом с эффектом и отменяй предыдущий запрос.
- Игнорируй устаревшие ответы. Если отмена недоступна, применяй только ответ с последним request id.
- Оптимистичное обновление допустимо только с откатом: сохрани предыдущее состояние, при ошибке верни его и покажи действие повтора.

## 7. HTTP, Zod, ошибки

- Держи один настроенный Ky-клиент в `shared/api`. Не создавай клиент на каждый запрос.
- Компоненты не импортируют Ky. Запросы вызываются из page/entity API или route loader.
- Валидируй внешние данные Zod на границе: ответ API, env, search params, формы, socket payload.
- Типы выводи через `z.infer`. Не дублируй тип вручную.
- Для форм используй `safeParse`; для API — `parse` с нормализацией ошибки.
- Не подавляй ошибки через `as` или пустой `catch`.

```ts
// shared/api/http.ts
import ky from 'ky';

import { env } from '@/shared/config/env';

import { addAuthHeader } from './add-auth-header';

export const http = ky.create({
  prefixUrl: env.API_URL,
  timeout: 15_000,
  retry: { limit: 2, methods: ['get'] },
  hooks: {
    beforeRequest: [addAuthHeader],
  },
});
```

```ts
// pages/orders/api.ts
import { z } from 'zod';

import { http } from '@/shared/api';

const ordersSchema = z.array(
  z.object({
    id: z.string(),
    title: z.string(),
  }),
);

export const ordersApi = {
  getOrders: async (signal?: AbortSignal) => {
    const data = await http.get('orders', { signal }).json<unknown>();
    return ordersSchema.parse(data);
  },
};
```

Нормализуй ошибки на границе API:

```ts
type AppError = {
  kind: 'network' | 'auth' | 'validation' | 'server' | 'unknown';
  message: string;
  fields?: Record<string, string>;
  cause?: unknown;
};
```

- Не показывай пользователю сырой `error.message` от сервера.
- Технические детали — в лог, пользователю — понятное сообщение и действие.
- Не логируй токены и персональные данные.
- Retry — только для идемпотентных запросов. Не повторяй POST автоматически.
- 401 обрабатывай централизованно в `app` или `shared/api`, без циклов редиректов.

## 8. React Router

- Добавляй React Router только при наличии нескольких экранов или URL-состояния. Для одного экрана роутер не нужен.
- Используй React Router. Не добавляй `atomic-router` и другие router-обёртки.
- Конфигурацию маршрутов держи в `app/router`. Страница не создаёт свой роутер.
- Загружай страницы лениво. Настрой `errorElement` и маршрут 404 на уровне роутера.
- Guards и проверку авторизации держи в layout-route или `app/router`. Не дублируй проверку в страницах.
- Параметры маршрута валидируй Zod. Некорректный параметр ведёт на ошибку или 404, а не в сломанный экран.
- URL-состояние (`page`, `sort`, `search`, `tab`) читай и обновляй через `useSearchParams`, а не через `window.history`.
- Не импортируй страницу в страницу. Навигация — через `<Link>`, `useNavigate` или общий path-контракт.
- Держи строку пути в одном месте: в `app/router` или рядом со страницей, если путь нужен только ей. Выноси в `shared/router/paths.ts` только при 2+ потребителях.
- Route loader используй для данных, без которых экран не имеет смысла. Импортируй только public API страницы, не её внутренние файлы.

```tsx
// app/router/router.tsx
import { createBrowserRouter, Navigate } from 'react-router';

export const router = createBrowserRouter([
  {
    element: <AppLayout />,
    errorElement: <RouteError />,
    children: [
      { index: true, element: <Navigate to="/orders" replace /> },
      {
        path: 'orders',
        lazy: async () => ({
          Component: (await import('@/pages/orders')).OrdersPage,
        }),
      },
      { path: '*', element: <NotFoundPage /> },
    ],
  },
]);
```

- Держи локальное состояние как можно ближе к месту использования; не поднимай его в стор без необходимости.
- Показывай загрузку, пустоту и ошибку явно. Не оставляй пустой экран на время запроса.
- Валидируй форму Zod-схемой рядом с формой или в бизнес-модели страницы.
- Маппь серверные ошибки на поля. Не сбрасывай введённые данные при ошибке.
- Блокируй submit во время отправки и предотвращай повторную отправку.
- Используй семантические кнопки, label, focus и клавиатурную навигацию.
- Стили держи рядом с компонентом (`*.module.css` или принятый в проекте способ). Глобальные токены — в `app/styles`.
- Не используй глобальные селекторы для компонентов.
- Пиши все компоненты с нуля. Общие примитивы и дизайн-систему держи в `shared/ui`, одноразовые — в `ui` страницы. Не подключай UI-библиотеку.
- Держи тёмную премиальную эстетику с зелёными акцентами, шкалу отступов 2/4/8/12/16/20/24/32/40/48/64+ и иерархию кнопок: accent, secondary, outline, ghost, text; danger — отдельный tone.
- Стремись к уникальному, но конвенциональному и приятному для глаза интерфейсу без визуального шума и перегруза.
- Не добавляй `memo`, `useMemo`, `useCallback` без измерения или явной причины.

## 10. Тесты

- Клади тест рядом с кодом: `OrderCard.test.tsx`, `model.test.ts`.
- Проверяй поведение и контракт, а не реализацию.
- Тестируй страницу через её public API и пользовательские сценарии.
- Тестируй Effector-модель через `fork` и `allSettled`: события → эффекты → состояние.
- Мокай сеть на границе HTTP, а не внутри компонентов.

## 11. Миграция layer-first

- Не переписывай проект целиком. Новые страницы делай pages-first.
- Старую страницу улучшай при касании: сначала переноси код в страницу, если у него один потребитель.
- Не выноси код вниз «за компанию». Второй потребитель должен быть реальным.
- Сохраняй публичный API слайса на время переноса, чтобы не ломать внешние импорты.
- Перед переносом сложной логики добавь характеризационные тесты.
- После переноса удаляй пустые слайсы, папки и неиспользуемые экспорты.

## 12. Чек-лист

- [ ] Код с одним потребителем лежит у потребителя, а не в нижнем слое.
- [ ] Извлечение в нижний слой оправдано двумя реальными потребителями.
- [ ] Слайс не раздроблен на микрослайсы без необходимости.
- [ ] У слайса один `index.ts` с явными экспортами, без `export *`.
- [ ] `model` не раздроблен на `store.ts` и `effects.ts` без необходимости; файлы названы по бизнес-контексту.
- [ ] Нет глубоких импортов и импортов слайсов одного слоя.
- [ ] Нет циклов зависимостей.
- [ ] Имена файлов не дублируют контекст папки.
- [ ] Нет пустых слоёв, папок и файлов «на будущее».
- [ ] У асинхронного состояния явные `idle`, `pending`, `success`, `error`.
- [ ] Есть пустое состояние, ошибка и действие повтора.
- [ ] Запросы отменяются или игнорируют устаревшие ответы.
- [ ] URL-состояние валидируется и не дублируется в сторе.
- [ ] Компоненты не вызывают API напрямую.
- [ ] Формы валидируются Zod и не теряют данные при ошибке.
- [ ] Параметры маршрута и внешние данные валидируются.
- [ ] Нет `any`, пустых `catch` и подавленных ошибок без причины.
- [ ] Нет UI-библиотек и новых зависимостей без явной необходимости.
- [ ] Изменения не ломают типы, линт и тесты проекта.

## 13. Стек

| Технология | Когда использовать |
|---|---|
| React | Всегда |
| React Router | Только при наличии роутинга |
| Zod | Валидация внешних данных, форм, env, URL |
| Effector | Состояние, события, эффекты |
| Ky | HTTP-запросы |

В существующем проекте бери версии из `package.json` и lock-файла, не меняй их без явного запроса. В новом проекте — последние стабильные версии. Для новой библиотеки проверь актуальную стабильную версию и совместимость с существующими зависимостями.
